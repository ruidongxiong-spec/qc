# 论文解读与复现边界

## 第一创新点与实现映射

论文的贡献是把长期轨迹推理重构成受约束状态转换：规划器产生带输出格式、事实约束和依赖关系的 DAG；执行器仅获得直接父节点的已验证 Capsule；工具观察压缩为 `new_findings`、`missing_info`、`new_leads`；独立 verifier 决定 Pass / Uncertain / Rejected；只有 Pass 可以传播。

实现中 findings 去重追加，missing_info/leads 每次替换以允许移除已解决问题。Rejected 反馈转成负约束，Uncertain 转成补充证据要求。每节点最多 8 次动作；每步至多一个工具调用；Finish 验证占一步。工具观察交给温度 0 的提取器，规划器/验证器温度 0.7，top_p=1。Executor 温度论文未明确，当前取 0.7。

Capsule 保留 result、evidence、confidence、rationale 及节点 ID/status。rationale 仅保存简短约束检查摘要和纠正建议，不要求模型披露内部思考链。confidence 是模型自报数值，校验范围但未做校准；论文没有给出置信度阈值，当前不臆设阈值。

## 必须公开的实现选择

1. **超时语义冲突**：论文式 (1) 限制全局记忆只含 Pass，但算法第 28 行将 ForcedSeal 结果加入记忆。本实现遵循严格门控：超时结果独立存入 partials，依赖它的节点标记 blocked。最终合成只使用 verified memory，并标明 unresolved。这样不会把未验证状态伪装成可靠事实，但可能降低完成率，需要后续对照实验。
2. **512-token 限制**：Windows 免费运行脚本默认加载对应 tokenizer.json，对整个序列化 Capsule（包含 ID/status/rationale）计数，限制 512 tokens，记录 tokenizer SHA-256。通用 CLI 使用 `--tokenizer` 启用；未提供时保留显式标记的 `utf8_bytes_legacy` 兼容模式。论文没有公布 tokenizer 版本和序列化规则，不能宣称与作者逐 token 一致。超预算要求缩短，不截断证据。详见 [本轮机制与优化](paper-aligned-optimizations.md)。
3. **验证上下文**：工具日志最多取末尾 15,000 字符，另附压缩状态和候选 Capsule。原文未给日志准确序列化方式。
4. **Python**：只开放无调用、无属性访问、无幂运算的算术表达式。完整代码执行需要独立隔离服务、超时和资源限制，当前未提供。
5. **无结构记忆消融**：将轨迹加入局部和父节点上下文，仍保留结构化抽取/验证接口。这是轨迹增强近似变体，不是完全移除 Capsules。无验证变体将候选直接提交并在 rationale 标注，禁止将它产生的 Pass 当作真实已验证证据。
6. Windows 脚本默认使用 Ollama 原生 JSON Schema 解码；语义约束仍由运行时和独立验证器检查。每个角色默认最多一次格式修正，执行器使用节点步数。规划修正耗尽会记录失败；最终合成无效则拒答；强制提取无效则保留未解决状态。工具可恢复错误反馈到局部状态；基础设施故障记录为运行失败。分段提取和重复动作后的 Finish 调度属于工程扩展，不是论文公布的原始实现。

## 尚不足以重现论文数字的材料

- HotpotQA / MuSiQue 各 1,000 条样本的版本、划分、样本 ID、2/3-hop 及难度分组、抽样种子。
- Bamboogle 125 条数据的确切版本，以及样本污染控制。
- 三个 Qwen3 模型的完整模型 ID、量化/推理配置、API 服务及执行器温度。
- 原始 Planner / Executor / Extractor / Verifier / Synthesizer 和 GPT-4o judge 提示词。
- 搜索日期、区域、语言、缓存和抓取策略；搜索结果随时间变化。
- 对齐模型的 ReAct / MindSearch 基线代码和完整计费、token、延迟日志。

论文 Table 1 的 Bamboogle Qwen3-30B 为 78.0%，而 125 题单次二元准确率以 0.8% 为步长；即使平均三次也不能精确得到一位小数 78.0%。需要作者确认是否使用不同样本数/平均方式。当前不据此修改数据或目标指标。

## 远程实验顺序

1. 配置模型端点和凭据，先运行一题，检查真实工具调用、证据来源、Capsule 和验证反馈。
2. 冻结数据 ID 和配置，跑小批量并人工抽查 verifier 假阳性/假阴性。
3. 用相同数据、模型、工具设置比较 full 与消融，执行三次；分别报告 EM/F1、语义准确率、未完成率、重试次数、耗时和 token/费用。当前 CLI 的 evaluate 输出 EM/F1、可选语义准确率与耗时；完整费用与分类统计需要后续分析，不能视为已测。
4. 记录实体消歧、约束放松、规划、检索和验证错误，复核论文所述瓶颈。
5. 第二创新点优先作为假设：可追溯约束覆盖检查或风险自适应验证预算。先设计受控对照及成本指标，不宣称创新性或性能收益已经成立。
6. 最后增加前后端可视化：DAG、验证事件、证据与状态面板；复用现有 JSON 结果作为接口基础。
